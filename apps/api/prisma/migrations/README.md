# Database migration contract

`20261026000000_initial` is an atomic baseline for an **empty PostgreSQL 16** database. It contains the Prisma-generated tables/enums/unique indexes and 181 foreign keys with `ON DELETE RESTRICT`, followed by reviewed SQL-only checks and five partial indexes. There are no cascading history deletes or destructive statements. `migration_lock.toml` pins PostgreSQL. `User.avatarKey` is the accepted P1-BE-IDENTITY request; no enums or serialization conventions changed.

From the repository root, with the local `.env` supplied by P0:

```sh
pnpm --filter @lms/api db:deploy
pnpm --filter @lms/api db:seed
pnpm --filter @lms/api db:generate
pnpm --filter @lms/api exec tsx --test prisma/tests/database.test.ts
```

The last command creates a fresh `lms_test_p1d_<pid>` database on localhost:55432, verifies PostgreSQL 16, deploys migrations, checks migration status, seeds, generates the client and tests actual writes (including competing attempt starts). It reruns the seed and compares every persisted row, including IDs/timestamps/password hashes and a manual profile edit. Its teardown drops only the database it created. The shared development database is never reset by tests. The local database role must have CREATEDB permission. Tests are opt-in because the default API Jest configuration owns `src` tests only.

## SQL coverage

- Platform versus tenant role restrictions; canonical email, coupon and slug values. Inputs must normalize before insertion: checks reject rather than silently rewrite history.
- Positive/nonnegative numeric fields and bounded percentages, including Decimal NaN rejection; lowercase three-letter currencies; overflow-safe bigint arithmetic for order and line money equations; quantity exactly one; strictly positive refunds.
- Ordered optional cohort/enrollment/assessment/release/coupon/period/token/deadline windows. Due date may equal the hard cutoff; zero-duration attendance is valid.
- Discriminated release, coupon, payment-source and grant shapes. Manual grants require a grantor and nonblank reason; subscription grants require a nonnull **finite** expiry. One-time prices cannot carry recurring interval-count/trial settings.
- Self-prerequisite/refresh-parent rejection; one open attempt across all versions per assessment/enrollment; one published assessment version; global notification preference uniqueness despite NULL workspace IDs; pending outbox/webhook lookup indexes.
- Section and Lesson positions intentionally allow temporary negative values for the documented transactional reorder protocol. All final positions must be validated by the content service before commit.

## Service invariants (not SQL CHECK guarantees)

## Rollout and backfill

There is no backfill for a genuinely empty database. Deploy with `prisma migrate deploy` before starting new API/worker code, then generate the client during build. Do not run `db push`, reset a shared database, or resolve this migration as applied without comparing its actual schema and custom SQL. Review nullable avatarKey handling before its API write is enabled.

For an existing populated deployment, **do not replay this baseline**. Inventory migration history, back up and verify restoration, reconcile the actual baseline, and coordinate a separately reviewed migration. Audit normalization collisions before updating emails/slugs/coupons (tombstones remain reserved), reconcile financial equations and invalid source shapes, then add large-table CHECKs as NOT VALID and VALIDATE after backfill. Build new large-table indexes CONCURRENTLY in a separate migration outside a transaction. Preserve partial indexes and checks when reviewing future Prisma-generated SQL; Prisma does not fully represent them in this schema.

Later changes use expand → backfill → contract so old API instances and leased jobs remain compatible. Never edit an applied migration checksum; append a new serialized migration and regenerate. Roll back application behavior only when compatible, prefer forward repair for schema/data, and keep immutable ledgers/grades/grants/certificates/audit evidence. An operational restore requires the deployment's backup/PITR process; no automatic destructive down migration is supplied.
